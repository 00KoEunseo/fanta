# 검증 절차

시뮬레이션은 한 곳을 고치면 멀리 떨어진 곳까지 흔들린다. 그래서 고치기 전과 후를 같은 잣대로 잰다.

## 도구

| 명령 | 하는 일 | 시간 |
|---|---|---|
| `npm run check` | 타입 검사 | 수 초 |
| `npm run audit:quick` | 150년 세계 1개 + 생애 4개 | 약 1분 |
| `npm run audit` | 300년 세계 3개 + 생애 16개, 기준선과 비교 | 약 4분 |
| `npx tsx scripts/qa/audit.ts --lives=40` | 생애만 40개 (생애 지표를 큰 표본으로 비교) | 약 6분 |
| `bash scripts/qa/baseline.sh [커밋] [옵션]` | 그 커밋의 코드로 기준선을 다시 만든다 | 위와 같음 |
| `npx tsx scripts/qa/save-size.ts <시드> <년>` | 저장 파일에서 무엇이 자리를 차지하는지 | 약 1분 |

- 불변식(✗)은 반드시 통과해야 하는 규칙이다. 예: 같은 시드는 같은 결과, 사별은 일대기에 남는다, 미성년은 여행 사건을 받지 않는다.
- 경고(⚠)는 나쁜 신호지만 당장 실패는 아니다. 예: 성능, 명품 쏠림.
- 지표는 기준선 대비 변화율로 본다. ◀는 30% 넘게 변한 것이다. 생애 지표는 표본이 작아 50%를 기준으로 본다.

## 절차

1. **고치기 전:** 작업 트리가 깨끗한지 확인한다(`git status`). 기준선이 직전 커밋과 맞지 않으면 `bash scripts/qa/baseline.sh`로 다시 만든다.
2. **고친 뒤:** `npm run check` → `npm run audit:quick` → `npm run audit` 순서로 돌린다.
3. **영향 점검:** 바꾼 함수·데이터를 쓰는 곳을 모두 찾아 확인한다(`grep`). 특히 아래 항목을 본다.
   - 반환값·인자 모양이 바뀌었는가
   - 난수(`w.rngSim`)를 새로 쓰거나 덜 쓰게 되었는가. 그러면 이후 모든 결과가 달라지므로, 지표 변화가 잡음인지 큰 표본으로 확인한다
   - 저장 파일에 새 필드가 생겼는가. 그러면 `save.ts`에 옛 저장을 위한 보정이 필요하다
   - 관전 세계 지표가 바뀌었는가. 플레이어 쪽만 고쳤는데 세계 지표가 움직이면 의도치 않은 연결이 있다는 뜻이다
4. **커밋:** 검증 결과 요약을 커밋 메시지에 남긴다. 기준선은 의도한 변화가 확인된 뒤에만 갱신한다.

## 알려진 한계

- 한 생애는 아주 작은 변화에도 전혀 다르게 흘러간다(나비 효과). 개별 생애의 결과로 판단하지 말고 평균으로 본다.
- 생애 검증은 고정된 규칙으로 선택지를 고른다. 사람이 고르는 경향과는 다르다.
- 화면(UI)은 자동 검증하지 않는다. `npm run build` 통과와 코드 점검까지만 한다.
